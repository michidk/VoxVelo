# AGENTS.md

VoxVelo is a family of three Fabric mods for Minecraft 26.3 (Java 25), versioned and released together.
README.md describes the features; this file is for working on the code.

## Modules

| Module | Mod ID / namespace | Java package | What it is |
| --- | --- | --- | --- |
| `bikes/` | `voxvelo_bikes` | `dev.michidk.voxvelo.bikes` | Bikes, physics, recipes, keyboard riding, track generator. Needs Fabric API and GeckoLib. |
| `fitness-lib/` | `voxvelo_fitness_lib` | `dev.michidk.voxvelo.fitnesslib` | Generic fitness service: Bluetooth trainers/sensors, OpenBikeControl, HUD, ride recording, FIT export. Knows nothing about bikes. |
| `fitness/` | `voxvelo_fitness` | `dev.michidk.voxvelo.fitness` | Adapter joining the two: bike controls, terrain resistance, road following, rider stats. |

- `bikes` and `fitness-lib` must never depend on each other; only `fitness` depends on both. Code both
  need is duplicated per mod (for example `client/ui/SettingsScreen`, `SettingsList`, `Tips`), so change
  both copies together.
- `fitness` plugs into `bikes` through the `voxvelo_bikes-extension` / `voxvelo_bikes-client-extension`
  entrypoints, and into `fitness-lib` through its public API.
- The public API of `fitness-lib` is `dev.michidk.voxvelo.fitnesslib.api` (documented in
  `docs/fitness-api.md`, example in `examples/fitness-boat/`). Everything else there is internal.
- Each module has `src/main` (common) and `src/client` (client-only) source sets. Client code must not be
  referenced from `main`; dedicated servers load without it.
- Translations live in `<module>/src/main/resources/assets/<mod id>/lang/en_us.json`. A control's tooltip
  is its label key plus `.tip` (see `Tips.of`).
- `native/ble/` is the Rust Bluetooth library packed into `fitness-lib`. Without `cargo` (and without
  `-PbleNatives=<dir>`) the jar builds anyway and the mod reports Bluetooth as unavailable.
- Verification programs for all modules live in `src/verification/java` and run as Gradle `verify*` tasks.

## Build and check

```sh
./gradlew build            # all three jars, plus check: spotlessCheck and every verify* task
./gradlew spotlessApply    # fix formatting (tabs, import order, no unused imports)
./gradlew :bikes:build     # bikes alone, as CI checks it standalone
```

Jars land in `<module>/build/libs/`. `./gradlew build` must pass before committing. When the change adds
logic that can be checked without a running game, add or extend a `verify*` program for it.

There is no JDK in the VibePod container; build with Docker, as root because existing build directories are
root-owned:

```sh
docker run --rm -e GRADLE_USER_HOME=/g -v voxelvelo-gradle:/g -v "$PWD":/workspace -w /workspace \
  gradle:9.7.1-jdk25 gradle --no-daemon build
```

Running `spotlessApply` that way leaves source files owned by root; prefer `spotlessCheck` and fix by hand,
or chown afterwards.

UI and rendering changes need a look in the game; a compiling build does not show layout problems.
Settings pages use the vanilla options layout and must stay usable at GUI scale 3 on a 1280x720 window.

## Conventions

- Match the surrounding code: tabs, `this.` on members, Javadoc on classes and non-obvious methods
  written as plain sentences about behaviour.
- Commit messages and PR titles follow Conventional Commits with the mod as scope where it helps, e.g.
  `fix(fitness-lib): reconnect trainer after sleep`. Mark breaking changes with `!` or a
  `BREAKING CHANGE:` footer.
- `CHANGELOG.md` is generated by git-cliff from the commits (`cliff.toml`, see `docs/releases.md`); do not
  edit it by hand.
- Releases are tag-driven (`v<mod_version>`) through `.github/workflows/release.yml`.
- Do not commit agent or tool state (`.claude/`, `.agents/`, `.gitnexus/`, `.codex/`, `.serena/`).
